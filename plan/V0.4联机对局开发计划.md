# V0.4 联机对局开发计划

最后更新：2026-08-13

状态：规划草案，待人类确认后进入实现

V0.4 承接已通过人工验收的 V0.3，目标是把游戏从「本地玩家对脚本 Bot」推进到「双端经互联网服务器中转的真实联机对战」。原路线图中 V0.4 定为「联机前工程结构整理」，但该工程拆分已在 V0.3 之前提前完成（见决策记录 2026-08-13 `x1l/V0.1V0.2工程模块化拆分`），因此 V0.4 腾出，直接承担原属 V0.5 的「最小联机对局原型」目标，并采用确定性锁步架构。

本计划中除「已确认基础」外，其余阶段拆解与默认参数可随实现调整。

## 版本目标

V0.4 的目标是证明游戏可以从本地原型进入真实双端互联网对战，并建立可维护的联机工程基础。

需要验证的问题：

- 确定性锁步在当前 Godot 4.5 + GDScript 环境下能否稳定跑通整局而不 desync。
- 定点数化后，单位过桥、碰撞分离、索敌、攻击距离的行为与 V0.3 观感是否一致；移动量化是否可接受。
- 玩家输入经命令层 → 锁步调度 → 双端同步执行的链路是否能让本地与远端表现一致。
- 云服务器只做中继 + 房间码 + 结果持久化、不承担任何战斗计算时，互联网对战是否稳定。
- 房间码建房/加入/准备/开始/结算/结果落库的最小流程是否跑得通。
- 断线「暂停等待 + 超时判负」是否足以覆盖 V0.4 的网络异常场景。

## 已确认基础

- V0.1/V0.2 已完成人工验收；V0.3 已完成 P1/P2/P3 与文档，待人工验收。
- V0.1/V0.2 单文件原型已提前完成模块化拆分（config/simulation/presentation/support 四层 + 精简控制器），出牌统一经 `BattleSimulator.try_play_card`，模拟器用 `running` 标记解耦 UI。
- 当前仍使用 Godot 4.5 stable + GDScript，主要目标用户为手机竖屏（V0.4 联机验证先在桌面端跑通，移动端导出留待 V0.6）。
- 已确认最终产品方向需要联机对战；V0.4 直接实现联机（原 V0.5 目标前移）。
- 联机架构：**确定性锁步**。双端各自跑完整模拟，只同步玩家输入命令；服务器不跑战斗逻辑。
- 确定性保证：**定点数整数运算**。位置/距离/半径/速度改用整数定点，避免浮点与 `sqrt` 导致的跨端 desync。
- 服务器角色：**中继 + 房间码 + 仅持久化对局结果**。服务器用 Python asyncio 标准库 TCP 实现，无第三方依赖，符合「服务器不应承担计算」约束；不跑战斗模拟。
- 验证范围：**互联网经云服务器中转**（用户具备公网 IP 的 Linux 云服务器）。
- 房间与匹配：**房间码**，不做账号、正式匹配、好友或排行榜。
- 断线处理：**暂停等待 + 超时判负**，V0.4 不做完整断线重连/状态重同步。
- 持久化范围：**仅对局结果**（胜负、结束时间、房间码），无账号维度累计。

## 推荐开发阶段

### P0：输入命令层 + 确定性模拟基础

目标：把模拟改造成「按固定 tick 推进、输入经统一命令层」，为锁步打基础，此阶段还不联机。

交付：

- 定义玩家意图命令结构，至少包含：`tick`、`side`、`card_index`、`target_x`、`target_y`（坐标用定点整数）。本地玩家、远端玩家与脚本 Bot 都经此命令入口驱动 `try_play_card`。
- 把模拟从 `_delta_time`/帧驱动改为固定步长 tick 驱动：控制器用累加器推进 tick，`BattleSimulator.advance_time` 与 `update_units` 按固定步长计算，不再依赖帧 delta。
- 共享随机种子：服务器在对局开始时下发种子，替代当前固定 `10101`；`rng` 推进路径在双端必须完全一致。
- 确定化遍历与排序：单位数组生成顺序确定化；索敌/距离排序的 tie-break 规则确定化（例如按单位 id 升序）。
- 记录 V0.3 联机前风险记录中尚未处理项的处置方式。

验收：

- headless 冒烟脚本用固定步长 + 固定种子连续跑 N tick，两次运行状态完全一致（自一致性）。
- 现有玩法行为/数值不随本次改造发生变化（对照 V0.3 表现）。
- Godot headless 主场景加载检查通过。

### P1：定点数化 — 几何与数值确定性

目标：消除浮点与 `sqrt` 跨端分歧，使模拟在双端可重放。

交付：

- 引入定点数表示（整数 Q 格式，建议初值 `*1000`，精度不足再调），覆盖位置、半径、距离、速度。
- 重写 `scripts/support/map_math.gd`：阵营换算、基地/桥位置、部署区裁剪、点到线段距离改用整数运算；距离比较统一用平方距离，避免 `sqrt`。
- 重写 `scripts/simulation/battle_simulator.gd` 几何/移动/碰撞分离/索敌/攻击距离：移动用整数向量归一化或预计算方向；碰撞分离用整数推算；射程判定用平方距离（沿用 V0.3「射程含自身半径」机制）。
- 卡牌数值（速度、半径、范围）从 `cards.json` 读取后转为定点；法术落点与 AOE 改整数。
- 表现层 `scripts/presentation/ui_painter.gd` 读取定点状态并换算到屏幕像素（仅客户端本地，不参与同步）；`evolution_flashes` 等纯客户端 UI 状态保持本地。
- 沿用 V0.3 确认的边界与碰撞约束：寻路边界用 `>=`/`<=`；所有单位有碰撞箱；`_separate_units` 攻击锁定逻辑保留。

验收：

- 本机双实例同种子锁步自跑 N tick，状态校验和完全一致。
- 单位过桥、碰撞、索敌、攻击行为与 V0.3 人工观感一致；移动量化手感可接受（若不可接受，提高定点精度并记录）。
- Godot headless 加载检查通过。

风险与取舍：

- 定点化可能轻微改变移动手感（量化误差），需人工确认可接受；这是本阶段最大不确定性。
- 若某处行为对照 V0.3 出现明显偏差，应记录差异点并询问人类，不自行调数值掩盖。

### P2：锁步同步核心

目标：实现锁步调度与 desync 检测，本机双实例跑通完整对局。

交付：

- 锁步调度器：固定 tick（建议 20Hz，可调），输入延迟（建议 2 tick ≈ 100ms，可调）；本地玩家输入延迟后执行，等待远端同 tick 输入到达再推进该 tick。
- 命令队列：每 tick 收集双方 Command，缺任一方则暂停模拟等待。
- 状态校验和：每 N tick（建议 10 tick）计算全状态哈希（单位 id/位置/hp、基地 hp、双方费用、`battle_time`、`rng` 状态），双方交换比对；不一致即标记 desync，暂停并提示。
- 本地双实例联机链路（不经云服务器，本地端口互通）：能完成完整对局，校验和始终一致。
- desync 处理默认：暂停并提示「同步错误，建议重开」，不自动判和。

验收：

- 本机双客户端锁步完成完整对局，无 desync。
- 缺输入/断连时模拟正确暂停，不空跑。

### P3：中继服务器 + 房间流程

目标：搭建云服务器中继与房间码流程，双端能经服务器建立连接。

交付：

- Python asyncio TCP 服务器（标准库，无第三方依赖）：房间码创建/加入、房间→客户端映射、双方包中继（可靠有序）、对局结果持久化（写本地文件或 SQLite，仅胜负 + 结束时间 + 房间码）。
- Godot 客户端网络层：连接服务器、创建/加入房间、收发 Command 包。
- 房间界面：创建房间（得码）、加入房间（输码）、双方准备、服务器下发 seed + 开始 tick。
- 牌组同步：双方各自选 6 卡，准备时交换牌组并确认 seed；双方都模拟彼此牌组与单位。
- 服务器部署最小化：裸 IP + 端口，进程守护（建议 systemd），防火墙放行；暂不做域名/HTTPS。

验收：

- 两台不同机器经云服务器用房间码建立连接并完成一局。
- 服务器进程常驻稳定，重启后房间状态可清空（V0.4 不要求房间持久）。

### P4：互联网对战打通 + 断线处理

目标：端到端跑通真实互联网对战与异常处理。

交付：

- 端到端链路：双端经云服务器中转完成出牌、单位战斗、任务进化、基地胜负与结算。
- 断线处理：检测对端断开 → 暂停对局 + 倒计时等待 → 超时判负；不做完整重连。
- 网络诊断 UI：连接状态、延迟（ping）、暂停/等待提示、desync 提示（默认收起，调试时可开）。
- 对局结果上报服务器持久化，结算页可查本局结果。

验收：

- 跨互联网完成至少 3 局稳定对局，无 desync。
- 人为断网验证「暂停 + 超时判负」生效。
- 对局结果落库可查。

### P5：联机关收尾 + 文档/协作同步

目标：把 V0.4 联机成果固化到工程与协作文档。

交付：

- 保留脚本 Bot 作为离线/单机验证入口（共用 Command 层），明确其非联机替代。
- 更新 `开发文档/工程/技术约定.md`：联机架构（锁步）、定点数约定、服务器栈、网络命令格式、tick/输入延迟默认值；同时修复该文件遗留的 git 冲突标记。
- 更新 `开发文档/协作/当前状态.md`、`开发文档/协作/决策记录.md`（标记旧「V0.4=工程拆分」为 superseded，新增「V0.4=联机」决策）、`开发文档/协作/更新摘要.md`。
- 更新 `plan/后续版本路线图.md`：V0.4 改为联机对局，V0.5 释放为联机增强（重连、匹配优化、移动端前置等）。
- 整理 V0.4 验收清单与已知限制。

验收：

- 协作者能从文档清楚知道 V0.4 的联机架构、确定性与服务器边界。
- 旧路线图与当前状态不再互相冲突。

## V0.4 不做

- 账号、正式匹配、好友、排行榜或商业化系统。
- 完整断线重连/状态重同步（仅暂停 + 超时判负）。
- 移动端导出与竖屏真机联机验证（V0.6）。
- 新卡、新玩法、多层进化、局外任务配置。
- 正式美术与音效。
- 服务端权威架构（已按服务器算力约束排除）。

## 默认参数（可随实现调整）

- 模拟 tick：20Hz（每 tick 50ms）。
- 输入延迟：2 tick（≈100ms）。
- desync 校验间隔：每 10 tick。
- 定点数精度：Q*1000（初值，精度不足再调）。
- 服务器：Python asyncio 标准库 TCP，裸 IP + 端口，systemd 守护。
- 种子：服务器在对局开始时随机生成并下发双端。

## 当前需要人类确认

- 定点数精度（Q*1000）与移动量化手感是否可接受；若不可接受，是否提高精度或回退方案。
- tick 率 20Hz、输入延迟 2 tick 是否合适（建议联机跑通后按手感调整）。
- 是否保留脚本 Bot 作为单机/离线验证入口（默认保留）。
- 服务器部署细节：端口、防火墙、是否需要域名/HTTPS（V0.4 默认裸 IP + 端口）。
- desync 发生时的处理策略（默认暂停并提示重开，不自动判和）。
- 协作记录签名：AI 写入 `更新摘要`/`决策记录`/`当前状态` 前需要当前操作者签名。
