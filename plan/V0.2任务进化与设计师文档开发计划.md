## 版本目标

V0.2 的目标是在 V0.1 对局闭环上完成两个能力：

- 建立并维护面向设计师的卡牌数值说明文档，让设计师能读懂并编辑卡牌速度、血量、攻击力等信息。
- 完成任务与进化系统，让卡牌可以在局内追踪任务、完成任务并自动进化。

## 已确认边界

- V0.1 已完成，人工验收没有发现问题。
- V0.2 至少需要创建并维护一个“设计师文档”。
- 设计师文档应记录卡牌速度、血量、攻击力等信息。
- 设计师文档是说明文档，可以当成“有注释的 JSON 数据”。
- 设计师有阅读代码的能力，但需要完善的注释系统来找到自己正在编辑什么。
- 如果发现设计师文档变化了，应向设计师询问是否需要同步到工程数据或其他文档。
- V0.2 需要完成任务与进化系统。
- V0.2 中 8 张初版卡都需要有任务和进化。
- V0.2 中每张卡默认 1 个任务，暂时不做局外任务配置。
- V0.2 中进化先做 1 层。
- V0.2 中任务进度仅在局内生效，不跨局保留。
- 任务完成后沿用已确认长期规则：自动且不可避地进化到对应下一形态。
- 任务完成后，卡牌后续使用会变为对应进化版本；已经在场上的单位不受影响。
- 每张卡的具体任务条件和进化效果已由项目负责人确认，并已进入 V0.2 原型实现。

## V0.2 不默认做

- 不默认扩充新卡池，除非人类确认。
- 不默认引入联网、账号、长期养成或跨局进度。
- 不默认把设计师文档变成唯一数据源，除非人类确认同步方式。
- 不默认继续扩展每张卡的任务条件或进化效果；当前只实现项目负责人确认的一层路线。
- 不默认实现局外任务配置。
- 不默认实现多层或分支进化。
- 不默认改变 V0.1 已通过的基础战斗闭环，除非实现任务/进化必须调整。

## V0.2 基础开发完成记录

- 卡牌数据：`游戏工程/scripts/v01/card_catalog.gd` 已将 8 张卡的占位任务/进化字段替换为正式 `task` 与 `evolution` 数据。
- 对局实现：`游戏工程/scripts/v01/v01_game.gd` 已实现按阵营追踪局内任务、任务完成自动进化、进化后卡牌定义、伤害/击杀/基地命中事件、奥能巨像周期 AOE、裂天矢路径伤害、漫游弓手双目标攻击、底部卡牌栏任务进度和结算统计。
- 行为边界：任务完成后只影响后续出牌或施法；已在场单位保留生成时属性。
- 当前微调：费用自然回复为每秒 0.5 点；裂魂矢对基地伤害为 33；星屑漂流数量为 6；投火手攻击落点 AOE 为固定半径 2。
- 验证记录：本机曾运行临时 GDScript 冒烟脚本直接触发 8 张卡任务并检查关键进化数值，测试通过后已删除临时脚本；随后通过 Godot headless 主场景加载检查。

## 推荐开发阶段

### P0：V0.1 收尾与版本入口切换

目标：把 V0.1 状态标记为完成，并让后续协作者知道当前推进 V0.2。

交付：

- 更新当前状态页，记录 V0.1 人工验收通过。
- 更新 `AGENTS.md` 的当前版本计划入口为 V0.2。
- 保留 V0.1 计划文档作为历史与实现参考。
- 新增 V0.2 计划文档。

验收：

- 后续对话提到当前版本计划时，能定位到 V0.2 计划。
- V0.1 的完成状态不会被误读为仍在等待验收。

### P1：设计师文档 V1

目标：建立设计师可以直接阅读和编辑的卡牌数值说明入口。

交付：

- 新增或维护 `开发文档/设计/设计师文档.md`。
- 记录当前 8 张卡的费用、数量、生命、攻击力、攻击间隔、射程、速度、半径和关键规则。
- 区分生物卡与法术卡。
- 标明当前数值为 trial，避免误认为最终平衡。
- 以“有注释的 JSON 数据”为目标组织说明，让设计师能快速定位自己在编辑什么。
- 说明逻辑单位、速度单位和 V0.1 首轮调参中的单位半径倍率。
- 记录 V0.2 任务/进化基础边界和已确认的每卡具体效果。

验收：

- 设计师不读代码也能看懂每张卡的核心数值和定位。
- 开发人员修改卡牌数值时，能知道需要同步维护该文档。
- 发现设计师文档变化时，协作者知道要询问设计师是否需要同步到工程数据或其他文档。

### P2：任务与进化设计确认

目标：在开发前继续向人类确认每张卡的具体任务与进化效果，避免开发人员自行定案。

已确认：

- 8 张初版卡都需要有任务和进化。
- 每张卡默认 1 个任务。
- V0.2 暂时不做局外任务配置。
- V0.2 进化先做 1 层。
- 任务进度仅在局内生效。
- 任务完成后自动且不可避地进化到对应下一形态。
- 8 张卡各自的任务条件和一层进化效果已确认，详见 `开发文档/设计/已确认玩法基础.md` 与 `开发文档/设计/设计师文档.md`。
- V0.2 原型中，任务和进化先显示在底部卡牌栏、事件日志与结算统计中。

验收：

- 决策记录中有任务/进化基础边界的人类确认条目。
- 每张卡具体任务和进化效果已被人类确认，并已进入完整实现。
- `开发文档/设计/已确认玩法基础.md` 和设计师文档补充对应规则。
- 开发人员可以据此实现，不需要自行补设定。

### P3：数据结构与同步流程

目标：让卡牌数值、任务和进化规则能被代码读取，也能被设计师理解。

交付：

- 梳理当前 `card_catalog.gd` 中的卡牌字段。
- 为任务与进化定义清晰数据结构。
- 将 V0.1 的 `task_placeholder` 与 `evolution_placeholder` 替换或迁移为 V0.2 正式字段。
- 设计师文档作为说明文档维护，不直接默认为唯一数据源。
- 当设计师文档变化时，先询问设计师是否需要同步到工程卡牌数据。
- 尽量让数值与规则集中，避免散落在 UI 或战斗流程里。

验收：

- 新增任务或进化不需要改动大段战斗流程。
- 设计师文档与代码字段能一一对应或明确说明差异。
- 文档变化不会被开发人员静默同步或静默忽略。

### P4：任务追踪系统

目标：让每张已选卡在对局内可以追踪自己的任务进度。

交付：

- 对局开始时初始化已选卡的任务状态。
- 每张初版卡都初始化 1 个默认任务。
- 战斗事件能上报给任务系统，例如部署、伤害、击杀、承伤、命中、攻击基地。
- UI 显示任务名称、进度和完成状态。
- 任务完成只触发一次。
- 任务进度只在本局内存在，对局结束后清空。

验收：

- 能稳定追踪 8 张初版卡的默认任务。
- 任务进度与战斗事件一致，不因清屏或单位死亡重复结算。
- 新开一局时，任务进度从初始值重新开始。

### P5：自动进化系统

目标：任务完成后，卡牌自动且不可避地进化到对应形态。

交付：

- 任务完成后立即触发对应进化。
- 进化状态影响后续部署或法术效果。
- UI 明确显示卡牌已进化。
- 结算统计记录任务完成与进化触发。
- V0.2 只实现 1 层进化，不实现多层或分支。

验收：

- 已进化卡牌再次使用时体现进化效果。
- 进化不可取消，不需要玩家额外确认。
- 单局内进化状态清楚可读。

### P6：验证与复盘

目标：确保 V0.2 新系统没有破坏 V0.1 已通过的基础闭环。

交付：

- Godot 主场景加载检查。
- 至少一轮人工可玩验收清单。
- 调试信息中显示任务进度、完成次数、进化次数。
- 更新设计师文档、当前状态和更新摘要。

验收：

- V0.1 已通过的核心对局仍可正常完成。
- 任务和进化在一局内能被观察、触发和复盘。
- 设计师文档能反映当前实现的卡牌数值。

## 首轮验收标准

V0.2 可认为达到基础完成条件，当且仅当：

- V0.1 已完成状态被记录清楚。
- 设计师文档已存在，并记录当前卡牌速度、血量、攻击力等核心数值。
- 任务与进化基础设计已由人类确认并记录。
- 8 张初版卡都有 1 个默认任务和 1 层进化。
- 对局内可以追踪任务进度，且任务进度不跨局保留。
- 任务完成后能自动且不可避地触发进化。
- 进化会实际影响后续卡牌使用或单位/法术效果。
- 竖屏 UI 中有任务与进化状态展示。
- 结算或调试信息能帮助设计师复盘任务和进化触发情况。
- V0.1 的部署、费用、Bot、基地、清屏和胜负闭环没有退化。

## 当前开放问题

- 任务/进化 UI 的最终产品形态是否沿用底部卡牌栏，还是改为独立侧栏、弹出详情或复合显示。
- Bot 是否应在 V0.2 后续验收中配置包含法术的卡组，方便自动观察裂魂矢和星陨任务。
- 进化后视觉表现是否需要额外美术、音效或更明显的特效提示。
