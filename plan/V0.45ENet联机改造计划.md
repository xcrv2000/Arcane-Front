# V0.45 ENet 联机改造计划

最后更新：2026-08-20

状态：方向已由项目负责人确认（ENet 替换 TCP、中继服务器重写、优先网络性能）；主体实现已落地（Go ENet 中继 + Godot ENet raw packet + 去线上 NO_OP），P0–P5 中 P0–P4 的代码路径已完成初版，P5 弱网量化/双人验收仍待执行。

V0.45 是插入在 V0.4 与 V0.5 之间的联机传输层改造版本。它不改变 V0.4 已确认的确定性锁步、定点数、房间码、断线重连和 desync 自动重同步思路，而是把底层传输从“TCP + JSON Lines”替换为“ENet over UDP”，并顺带把锁步线上协议从“逐 tick 发送 NO_OP”改为“缺省即 NO_OP + 迟到真实命令回滚”。

## 背景

当前 V0.4 联机链路使用 `StreamPeerTCP + JSON Lines` 中继。TCP 是可靠有序字节流，在网络抖动时存在队头阻塞：一个包重传会让后续已经到达的包一起等，表现为“卡一下然后突然追帧”。同时当前锁步协议会预发大量 NO_OP 占位命令，进一步放大包量和队头阻塞。

此前 V0.4 已经把“发生 desync 后的恢复耗时”降到可接受范围，但用户反馈“卡顿频率仍然很高”。V0.45 的目标不是继续优化恢复速度，而是**降低卡顿/desync 的发生频率**。

## 版本目标

- 用 ENet 替换 TCP，消除 TCP 队头阻塞带来的延迟尖刺。
- 重写中继服务器，优先网络性能；服务器仍然只做中继、房间、命令日志和结果持久化，不跑战斗逻辑。
- 线上只发送“真实操作”和“校验和”，不再逐 tick 发送 NO_OP；缺省视为 NO_OP，迟到真实命令走本地回滚。
- 保留 V0.4 的锁步、定点数、检查点快速重同步、断线自动重连和 desync 自动恢复语义。
- 在弱网（丢包、抖动、高 RTT）下显著降低暂停频率和 desync 次数。

## 已确认边界

- 版本号记为 **V0.45**。
- 底层传输：**ENet over UDP**。
- 中继服务器：**可以重写**，优先网络性能；不采用服务端权威。
- 客户端仍然使用 Godot 4.5 + GDScript；客户端网络层改用 Godot 的 `ENetMultiplayerPeer` 以 raw packet 方式承载自定义协议。
- 战斗逻辑仍保持双端确定性锁步；服务器不参与战斗模拟。
- 房间码、无账号、只持久化对局结果、断线超时判负等 V0.4 已确认规则继续保留。
- 协作文档签名使用 `x1L`。

## 为什么选 ENet 而不是 WebSocket / 裸 UDP

- **WebSocket** 底层仍是 TCP，无法解决队头阻塞，对弱网锁步提升有限。
- **裸 UDP** 最灵活，但可靠有序、重传、去重、连接管理都要自己实现，原型阶段成本过高。
- **ENet** 是成熟的 UDP 可靠传输层，提供可靠/不可靠通道、重传、Ack、分包和连接管理；Godot 原生支持，且适合锁步类游戏。

参考链接：

- [Godot ENetMultiplayerPeer 文档](https://docs.godotengine.org/zh-tw/4.x/classes/class_enetmultiplayerpeer.html)
- [codecat/go-enet：Go 的 ENet cgo 绑定](https://github.com/codecat/go-enet)
- [rusty_enet：Rust ENet 实现](https://crates.io/crates/rusty_enet)

## 目标架构

```text
[Godot 客户端 A]
    │  ENet (UDP) 可靠通道: 房间控制/PLAY_CARD/CHECKSUM/RESULT/RESYNC
    │  ENet (UDP) 不可靠通道: 应用心跳/Ping
    ▼
[ENet 中继服务器]  ← 只转发 + 存命令日志 + 房间码 + 结果落盘
    ▲
    │  ENet (UDP) 同上
[Godot 客户端 B]
```

服务器不计算战斗，不保存完整战场状态；只保存：

- 房间状态（host/guest、牌组、seed、ready、started）。
- 命令日志（只记录真实 `PLAY_CARD` 和 `CHECKSUM`，不记录 NO_OP）。
- 结果文件 `match_results.jsonl`。

## 服务器技术选型

首选：**Go + codecat/go-enet**。

- 使用官方 libenet 的 cgo 绑定，与 Godot 客户端使用的 ENet 协议兼容性风险最低。
- Go 并发模型适合处理大量客户端连接与房间转发。
- 编译为单一二进制，部署简单；中继不做战斗计算，性能足以支撑目标。
- 若未来希望去掉 cgo / 纯静态部署，可评估 **Rust + rusty_enet**，但必须先做“Godot ENet ↔ rusty_enet 互通冒烟”。

不推荐继续使用 Python 标准库做 ENet 服务端，因为 Python 没有内建 ENet，且性能优先级已被用户明确置高。

服务器目录规划：

- 新增 `tools/relay_server_enet/`，保留旧 `tools/relay_server/relay_server.py` 作为 V0.4 回退/对照。
- V0.45 验收通过后，再将旧 TCP 中继标记为 deprecated，最终由 V0.45 服务器替换。
- 部署工具 `tools/deploy_relay/` 需要适配新服务器（上传二进制/源码、UDP 端口放行、重启、健康检查）。

## 客户端改造点

### 1. 网络层替换

- 删除/替换 `scripts/networking/network_client.gd` 的 `StreamPeerTCP` 实现。
- 使用 `ENetMultiplayerPeer.create_client(host, port, channels, ...)` 创建客户端。
- 以 raw packet 方式发送/接收自定义包，不依赖 Godot 的 RPC 系统。
- 保留上层信号接口，尽量让 `v01_game.gd` 的房间/对局流程改动最小：
  - `connected_to_server`
  - `room_created`
  - `room_joined`
  - `peer_joined`
  - `peer_ready_changed`
  - `start_match_received`
  - `command_received` / `commands_batch_received`
  - `result_received`
  - `resume_battle_received`
  - `resync_data_received`
  - `disconnected` / `peer_disconnected`

### 2. 通道与包格式

ENet 通道规划：

| 通道 | 可靠性 | 用途 |
|---|---|---|
| 0 | 可靠有序 | 房间控制、PLAY_CARD、CHECKSUM、RESULT、RESYNC、RESUME |
| 1 | 不可靠 | 应用心跳 / Ping / 网络状态采样 |

包首字节用于区分编码：

| 首字节 | 类型 | 载荷 |
|---|---|---|
| `0x00` | JSON 控制包 | `{ "type": ... }`，用于房间创建/加入/准备/结果等低频控制 |
| `0x01` | 二进制 PLAY_CARD | `tick:int32, side:u8, card_id_len:u8, card_id:bytes, target_x_fp:int32, target_y_fp:int32` |
| `0x02` | 二进制 CHECKSUM | `tick:int32, side:u8, checksum:u32` |
| `0x03` | 二进制 Ping/Pong | `send_time_ms:int64`（用于采样 RTT，可选） |

说明：

- 房间控制继续使用 JSON，便于扩展和调试；战斗高频命令使用二进制，降低包体与解析开销。
- 所有多字节整数使用小端序；Godot 与 Go 均原生支持。
- 服务器对 `PLAY_CARD` / `CHECKSUM` 只解析必要字段（tick、side、card_id、checksum）用于命令日志，然后原样转发。

### 3. 取消线上 NO_OP

这是 V0.45 最重要的锁步变化：

- 不再通过 `COMMAND_BATCH` 预发/补发 NO_OP。
- 锁步调度器把“某 tick 某方没有真实命令”视为 `NO_OP`，直接推进。
- 若之后收到迟到的真实 `PLAY_CARD`，使用 V0.4 已实现的回滚重放机制恢复：
  - 回滚到最早可用快照/检查点；
  - 替换该 tick/side 的 NO_OP 或旧命令；
  - 重放到当前 tick；
  - 重新发送修正后的 CHECKSUM。
- 这样可以大幅减少包量，并让缺命令不再必然触发暂停。

需要调整：

- `lockstep_scheduler.gd` 的 `strict_wait` 不再等待“对端 NO_OP”。
- `v01_game.gd` 中所有“预发 NO_OP 窗口”逻辑可移除或降级为本地占位。
- 保留命令缺失统计，但缺命令时默认先按 NO_OP 推进；连续缺失才主动向服务器请求真实命令日志。
- `Command.wrap_command_batch` / `COMMAND_BATCH` 可保留为兼容层，但 V0.45 主线上不再发送。

### 4. 断线重连与 desync 重同步

- ENet 自带连接断开事件；客户端在断开后仍按 V0.4 的 30 秒自动重连流程。
- 重连时重新 `create_client`，再发送带 `client_id` 的 `JOIN_ROOM`。
- 服务器继续使用 `client_id` 认领房间槽位。
- 命令日志、`RESUME_BATTLE`、`RESYNC_DATA` 语义不变，但包改为 ENet 通道 0 上的 JSON 或二进制混合格式。
- 服务器日志只记录真实命令后，断线重放/desync 重同步的数据量会更小。

## 协议草案

### 控制包（JSON，通道 0）

基本沿用 V0.4 协议，只去掉行分隔符（ENet 包本身就是边界）：

```jsonc
{"type":"CREATE_ROOM","client_id":"可选"}
{"type":"JOIN_ROOM","room_code":"ABC2","client_id":"可选"}
{"type":"READY","ready":true,"deck":["shield","swordsman",...]}
{"type":"HEARTBEAT"} // 可走不可靠通道
{"type":"RESYNC","tick":123,"base_tick":90}
{"type":"RESULT","winner":"host","room_code":"ABC2"}
{"type":"LEAVE_ROOM"}
{"type":"REMATCH","deck":[...]}
```

服务器推送：

```jsonc
{"type":"ROOM_CREATED","room_code":"ABC2","my_side":"host","client_id":"..."}
{"type":"ROOM_JOINED","room_code":"ABC2","my_side":"guest","client_id":"..."}
{"type":"PEER_JOINED"}
{"type":"PEER_READY","side":"guest","ready":true}
{"type":"START_COUNTDOWN","seconds":3} // 任一方取消准备时 seconds=0
{"type":"START","seed":123,"my_side":"host","my_deck":[...],"peer_deck":[...]}
{"type":"PEER_DISCONNECT","grace_seconds":30}
{"type":"OPPONENT_DISCONNECTED_WIN","winner":"host","room_code":"ABC2"}
{"type":"RESUME_BATTLE","seed":123,"my_side":"host","my_deck":[...],"peer_deck":[...],"target_tick":123,"commands":[...]}
{"type":"RESYNC_DATA","target_tick":123,"base_tick":90,"seed":123,"my_side":"host","my_deck":[...],"peer_deck":[...],"commands":[...]}
{"type":"RESULT","winner":"host","room_code":"ABC2"}
{"type":"ERROR","message":"..."}
```

### 战斗命令包（二进制，通道 0）

`PLAY_CARD`：

```text
byte 0        = 0x01
int32 tick    = 执行 tick
uint8 side    = 0=player, 1=bot
uint8 id_len  = card_id 字节长度
bytes id      = card_id（UTF-8）
int32 x_fp    = 目标 x（Q*1000）
int32 y_fp    = 目标 y（Q*1000）
```

`CHECKSUM`：

```text
byte 0        = 0x02
int32 tick    = 校验 tick
uint8 side    = 0=player, 1=bot
uint32 checksum = FNV-1a 32 位校验和
```

`PING` / `PONG`（不可靠通道）：

```text
byte 0        = 0x03
int64 time_ms = 本机发送时间戳（毫秒）
```

### 缺省 NO_OP 语义

- 服务器命令日志中不存在 `NO_OP`。
- 客户端在 `current_tick` 推进到某个 tick 时，若某方没有 `PLAY_CARD`，则本地用 `Command.no_op_command(tick, side)` 填充执行。
- 若之后收到该 tick 的真实 `PLAY_CARD`，触发回滚。
- 因此 ENet 可靠通道需要保证 `PLAY_CARD` 按 tick 有序到达；ENet 通道 0 的有序可靠性满足此要求。

## 服务器功能清单

新服务器 `tools/relay_server_enet/` 需要实现：

1. ENet host 初始化，监听 UDP 端口（建议默认 `8765/udp`）。
2. 客户端连接/断开事件管理。
3. 房间码创建/加入，`client_id` 重连认领。
4. 房间状态：host/guest、ready、deck、seed、started。
5. 命令日志：
   - 只记录真实 `PLAY_CARD` / `CHECKSUM`；
   - 按 `(tick, side)` 收敛最终命令；
   - 支持 `REQUEST_COMMANDS` 回查；
   - 支持 `RESUME_BATTLE` / `RESYNC_DATA` 尾部命令下发。
6. 对端转发：通道 0 可靠转发真实命令与控制包。
7. 心跳超时：应用层心跳 + ENet 断开事件共同判断，保留 30 秒宽限。
8. 结果持久化：`match_results.jsonl`，字段与 V0.4 保持一致。
9. 健康检查/日志：建议输出连接数、房间数、每秒转发包数、RTT 采样。

## 推荐开发阶段

### P0：协议互通冒烟

目标：证明 Godot ENet 客户端与新的 ENet 服务器能互通。

- 用最小 Go ENet 服务器实现 `CREATE_ROOM` / `JOIN_ROOM` / `PEER_JOINED`。
- Godot 客户端用 `ENetMultiplayerPeer` raw packet 收发 JSON 控制包。
- 验证 UDP 端口、通道 0/1、包边界、断开事件。
- 验证 codecat/go-enet（或备选 rusty_enet）与 Godot ENet 的协议兼容性。

验收：

- 两个 Godot 实例能创建/加入同一房间并收到 `PEER_JOINED`。
- 在 5% / 10% 丢包模拟下仍能通过 ENet 可靠通道完成房间流程。

### P1：服务器重写

目标：完成房间/中继/命令日志/结果持久化。

- 实现全部控制包处理。
- 实现二进制 `PLAY_CARD` / `CHECKSUM` 解析、日志、转发。
- 实现 `REQUEST_COMMANDS` / `RESUME_BATTLE` / `RESYNC_DATA` 的服务器侧命令回查。
- 实现心跳超时、断线宽限、超时判负。
- 更新部署工具：UDP 端口放行、二进制部署、健康检查。

验收：

- 服务器能同时承载多房间且命令日志正确收敛。
- 模拟客户端脚本可完成“建房→加入→READY→START→发命令→RESULT→持久化”全流程。

### P2：客户端网络层替换

目标：Godot 客户端从 TCP 切到 ENet raw packet。

- 新增 `scripts/networking/enet_client.gd` 或重写 `network_client.gd`。
- 新增 `scripts/networking/enet_protocol.gd` 负责二进制编码/解码。
- 保持 `v01_game.gd` 信号接口基本不变。
- 房间 UI 和准备流程继续复用。

验收：

- 两个 Godot 实例经 ENet 服务器完成创建/加入/准备/开始。
- 旧的 TCP 网络层不再被联机流程调用。

### P3：锁步去 NO_OP + 回滚适配

目标：线上只传真实命令，缺省即 NO_OP。

- 修改 `lockstep_scheduler.gd`：`strict_wait` 下缺真实命令不再暂停，按 NO_OP 推进。
- 修改 `v01_game.gd`：删除/停用 NO_OP 预发与 COMMAND_BATCH 发送。
- 保留并验证迟到 `PLAY_CARD` 的回滚重放。
- 调整弱网 HUD：显示 ENet RTT、命令缺失/回滚次数、desync 次数。

验收：

- 5% / 10% / 20% 丢包模拟下，暂停次数明显低于 V0.4 TCP 基线。
- 回滚能正确恢复状态，最终 checksum 一致。

### P4：重连与重同步验证

目标：断线重连、desync 自动重同步在 ENet 上跑通。

- 验证客户端断网重连后 `client_id` 认领。
- 验证 `RESUME_BATTLE` 尾部回放。
- 验证 `RESYNC_DATA` 检查点+尾部回放。
- 验证迟到 CHECKSUM 不再误报。

验收：

- 人为断网 10 秒后重连成功，战场恢复。
- 人为制造命令延迟/回滚场景，不发生结果页误判。
- 重同步失败时才显示“同步错误”。

### P5：性能与验收

目标：量化 V0.45 相对 V0.4 的提升。

- 建立弱网测试矩阵：0% / 5% / 10% / 20% 丢包，50 / 100 / 200ms RTT。
- 记录指标：
  - 每分钟暂停次数与总暂停时长
  - desync 次数
  - 回滚次数
  - 每局命令包总量/字节数
  - 可感知操作延迟
- 双人互联网真机/双机验收至少 5 局。
- 更新技术约定、当前状态、更新摘要。

验收：

- 在 10% 丢包 + 100ms RTT 下，暂停频率和 desync 次数显著低于 V0.4。
- 单机模式无回归。
- 服务器 CPU/内存占用可接受。

## V0.45 不做

- 不做服务端权威/状态同步。
- 不做账号、匹配、排行榜。
- 不做 DTLS/TLS 加密（ENet 本身无加密；V0.45 阶段接受明文 UDP，后续单独评估）。
- 不做移动端后台保活专项（V0.6）。
- 不新增卡牌、玩法或平衡内容。
- 不强制删除旧 TCP 服务器；只在新服务器验收通过后标记 deprecated。

## 风险与开放问题

- **服务器语言/绑定**：首选 Go + codecat/go-enet；若 cgo 部署不便，改用 Rust + rusty_enet 前必须先做互通冒烟。
- **Godot ENetMultiplayerPeer raw packet API**：需要确认通道设置、`put_packet`/`get_packet` 在自定义协议下的行为；若 API 不适合 raw packet，再评估直接用 GDExtension 封装 C ENet。
- **去 NO_OP 后的回滚边界**：回滚窗口仍受检查点保留时间限制；若命令迟到超过保留窗口，只能走服务器重同步，不能本地回滚。
- **UDP 穿透**：ENet 依赖公网服务器中转；双方 NAT 类型差异可能影响移动网络下的稳定性，先按“都有公网服务器中转”处理。
- **端口与防火墙**：从 TCP 8765 改为 UDP 8765；部署工具和文档需要同步。
- **旧协议兼容**：V0.45 不要求兼容旧 TCP 客户端；旧服务器保留到切换完成。
