## 当前 V0.1/V0.2 工程结构（已模块化）

V0.1/V0.2 原型已从单文件拆分为按职责分层的模块结构。以下是当前实现事实；后续可随 Godot 编辑器整理继续调整。

### 目录与职责

- `scenes/v01/V01Game.tscn`：V0.1 主场景，根节点为 `Control`，挂载 `scripts/v01/v01_game.gd`。
- `scripts/v01/v01_game.gd`：对局控制器（Control 节点入口）。仅负责生命周期、输入分发、每帧驱动模拟器与绘制器、屏幕状态切换；不再直接包含战斗逻辑或绘制实现。当前前置屏幕状态为 `MAIN_MENU / COMPENDIUM / DECK_BUILDER / ROOM_SETUP / ROOM_WAIT`，之后进入 `BATTLE / RESULT`。战斗选卡快捷键为 Q/W/E/A/S/D；为避免冲突，V0.3 调试快捷键中的 Bot 牌组切换与随机种子重置已由 D/S 调整为 B/Y，其余仍为 +/− 加费、T 强制完成任务、R 本地重开、F 调试面板开关。
- `data/cards.json`：16 张主卡（当前 15 张可携带、见习骑士征召 1 张禁用）与 3 个不可携带衍生单位的数值、任务、进化、标签和机制字段，是当前权威卡牌数据源；`deckable=false` 表示条目保留在图鉴/运行时目录但不得进入牌组。`tags` 可同时记录系列和机制标签；当前规范系列值为“星间飞行”与“百骸公国”。
- `scripts/v01/card_catalog.gd`：卡牌数据读取适配器，从 `res://data/cards.json` 读取并转换 Godot 运行时字段。`all_cards()` 返回包含禁用卡的完整主卡目录，`deckable_cards()` 只返回玩家/Bot 可携带主卡，`derivative_units()` 返回衍生单位，`all_runtime_cards()` 用于图鉴、任务与战斗模拟；`has_tag()` / `cards_with_tag()` 用于单卡判断与目录筛选。读取时会去除空白与重复标签，进化定义由基础卡复制，因此默认继承其标签。
- `scripts/config/game_config.gd`：集中存放平衡常量、地图尺寸、Bot 牌组与美术路径；各脚本以 `const Config = preload(...)` 引用，沿用 preload 风格，不使用 class_name。
- `scripts/simulation/battle_simulator.gd`：战斗模拟核心。纯逻辑，持有对局运行时状态（时间、费用、单位、基地、法术特效、持续区域、延迟召唤、固定 tick 法术弹道、卡牌内置冷却、统计、事件日志、进化闪光），驱动单位移动/碰撞分离/索敌/攻击、法术命中、召唤、阵亡触发、侍童成长光环、伤害转移、清屏与胜负结算。普攻结算会向非同步 `spell_effects` 队列写入短时 `attack` 表现事件；该队列不参与锁步 checksum，不得承载影响战斗结果的状态。
- `scripts/simulation/task_system.gd`：任务与进化系统。追踪局内任务进度、卡牌使用次数、完成时间戳，并支持侍童召唤/阵亡、同时在场和双方全场阵亡等全局任务；任务完成后自动进化卡牌。
- `scripts/simulation/bot_brain.gd`：Bot AI。支持随机从卡池选 6 张或使用固定牌组；两种入口先使用 `deckable_cards()` 排除玩家禁用卡，再过滤显式设置 `ai_deckable=false` 的卡（当前为百骸一心）；与玩家共用 `BattleSimulator.try_play_card` 入口；提供 `set_use_random_deck` 切换与 `current_deck` 查询接口。
- `scripts/presentation/ui_painter.gd`：屏幕绘制与布局。图鉴与牌组共用每页 8 项的仓库绘制，但图鉴使用完整运行时目录，牌组只使用可携带卡目录；图鉴详情显示条目的全部标签，并对 `deckable=false` 的主卡显示红橙色“禁用”徽标，对带 `derivative` 标签的不可携带单位显示蓝灰色“衍生”徽标。战斗卡槽显示 Q/W/E/A/S/D 键位标签，并在卡牌内置冷却期间置灰、显示剩余秒数。战斗地图绘制 `attack` 轨迹、命中闪光与 AOE 落点；攻击事件携带模拟阵营，绘制时与 `controlled_side` 比较，使本机我方始终为蓝青色、敌方始终为红橙色。单位图形下层按 `squire_death_buff.radius` 绘制淡色的附近侍童阵亡触发范围。
- `scripts/presentation/canvas_helpers.gd`：低层绘制原语（面板、文本、贴图）与单位美术加载/缓存/几何占位回退，当前回退形状支持圆、方、三角、菱形和六边形。
- `scripts/support/map_math.gd`：纯地图与几何工具（阵营换算、基地/桥位置、部署区裁剪、点到线段距离），无运行时状态。

- `assets/units/`：AI 单位美术透明 PNG；文件名为 `<art_id>_front.png` 与 `<art_id>_back.png`。
- `assets/units/source_sheets/`：AI 单位美术左右正背面源图；不应由游戏运行时直接引用。
- `project.godot`：已设置 `run/main_scene` 指向 V0.1 主场景，并设置 720x1280 竖屏优先视口。

### 当前牌组存档

- 当前只有一个供单机与联机共用的“当前牌组”，本地保存为 `user://selected_deck.json`。
- 存档结构为 `{schema_version, selected_card_ids}`；读取时会过滤不存在和重复的卡牌 id，只有恰好 6 个有效 id 才采用，否则回退为卡池前 6 张。
- 牌组界面使用草稿编辑：只有点击“保存牌组”后才覆盖当前牌组；未保存离开会恢复已保存牌组。
- 该文件是玩家本机数据，不进入仓库，也不参与联机锁步 checksum；联机准备包仍只发送最终 6 个卡牌 id。
- 图鉴可浏览禁用主卡与衍生单位，但牌组仓库和存档校验只接受 `deckable_cards()` 返回的可携带 id，因此禁用卡和衍生单位都不会进入单机或联机准备包；旧存档含已禁用 id 时会回退默认牌组。

### 模块间接口约定

- 控制器每帧顺序：`simulator.advance_time` → `task_system.check_mana`（双方）→ `bot_brain.update` → `simulator.update_units` → `simulator.update_spell_effects` → 检测 `simulator.running` 切换结算界面。顺序与拆分前一致。
- 出牌统一经 `BattleSimulator.try_play_card(side, card, position)`，`card` 为 `TaskSystem.active_card_by_id` 解析后的生效卡牌。
- 任务/进化事件通过 `TaskSystem` 回调 `BattleSimulator.record_task_completed` 与 `push_event` 回写统计与日志；`BattleSimulator` 在伤害/出牌时回调 `TaskSystem.track_*`。
- 模拟器与 UI 解耦：模拟器使用逻辑坐标与 `running` 标记，不依赖 `screen_mode`；绘制器读取模拟器状态但不修改。

### 当前调参实现

- `MANA_PER_SECOND = 0.5`；生物单位生成时使用 `UNIT_RADIUS_SCALE = 2.0` 放大卡牌数据中的单位半径，法术范围和基地半径不随该倍率变化。

## 坐标、速度与原型表现约定

- 对局地图的长边应作为 100 个逻辑单位处理，避免不同设备尺寸导致单位表现不同。
- 速度数值的单位是逻辑单位/秒；速度 1 表示每秒移动 1 个逻辑单位，速度 8 表示每秒移动 8 个逻辑单位。
- 实现时应优先让战斗逻辑使用逻辑单位，再按当前视口尺寸换算到屏幕像素。
- 不应把设备像素值作为权威移动速度或战斗距离。
- V0.1 中单位不需要美术资源；每个生物可用 Godot 绘制的简单几何图形（圆、三角、方）加一个字表示。
- 当前 AI 单位美术属于版本线外表现层实验：`v01_game.gd` 会按单位 `art_id` 读取 `assets/units/<art_id>_front.png` 或 `<art_id>_back.png`，并通过 `Image.load_from_file()` 创建运行时纹理；缺图时回退到 V0.1 几何占位表现。
- 当前 AI 单位美术实现不依赖提交 `.png.import` 文件；若 Godot 编辑器后续生成导入缓存，不应改变正式资源命名和 fallback 规则。
- AI 单位图片不参与碰撞、索敌、攻击距离、费用、任务或进化判定；这些逻辑仍使用 `unit["radius"]`、卡牌数值和任务状态。
- 卡牌权威数据文件 `游戏工程/data/cards.json` 不写入美术路径；基础形态使用卡牌 `id`，进化形态使用运行时 `evolved_id` 作为表现层 `art_id`。
- 蓝/红阵营识别环由 `v01_game.gd` 单独绘制，不烘焙进单位图片。

## 联机实现约束

- 奥术前线已确认最终需要联机对战；后续工程整理应避免继续把战斗逻辑、玩家输入、Bot 输入、UI 展示和本地状态强耦合在同一个不可拆脚本中。
- 已确认 V0.3 不直接实现联网，但应记录当前本地原型中会影响联网的假设，例如直接读写全局对局状态、随机数来源、输入命令格式、单位生成顺序和结算事件来源。
- 已确认 V0.4 直接实装联机对局（原「联机前工程准备」已提前完成）；架构为确定性锁步 + 定点数整数运算 + Python asyncio 中继服务器（中继/房间码/仅持久化对局结果）+ 互联网经云服务器 + 房间码无账号 + 断线暂停超时判负；详见 `plan/V0.4联机对局开发计划.md`。
- V0.5 释放为联机增强（断线重连、弱网优化、匹配增强等）；原 V0.5 最小联机原型目标已前移至 V0.4；仍不含账号、正式匹配、排行榜或商业化。
- V0.4 联机架构已工程实现落地：确定性锁步（双方同一 seed、同一定点模拟），中继服务器不承担战斗计算，仅承担房间管理、命令中继、START 共享种子与牌组下发、RESULT 持久化、断线超时判负。

### V0.4 当前默认联机参数

- 模拟固定 tick：60Hz（TICK_DT≈0.0167s），写入 `game_config.TICK_RATE / TICK_DT`。
- 输入延迟：4 ticks ≈ 67ms（`INPUT_DELAY_TICKS=4`）。即玩家出牌命令被调度到 `当前 tick + INPUT_DELAY_TICKS` 后执行，给网络 RTT 留窗口。
- 定点数精度：Q*1000（`FP_SCALE=1000`，`FP_SCALE_F=1000.0`）。所有位置、半径、速度、伤害、法力、射程使用 int，除法与 sqrt 只在必要处配合整数近似（优先平方距离避免 sqrt）。
- desync 校验间隔：每 30 ticks（0.5 秒，`DESYNC_CHECK_INTERVAL=30`）双方各自计算 `battle_simulator.state_checksum()` 并以 CHECKSUM 命令上报，由 scheduler 比对，不一致即 `scheduler.desynced=true` 并暂停。校验状态包含 RNG state、百骸公国动态单位属性、持续区域/延迟召唤、卡牌内置冷却、区域累计回费及任务进化进度。
- 断线策略：服务器 30 秒宽限（DISCONNECT_GRACE_SECONDS）；超时则断线方负，胜者通过 `OPPONENT_DISCONNECTED_WIN` 包通知。V0.4 不做完整重连恢复。
- 房间码：4 位大写字母数字（字母表 A~Z 去 O/I + 数字 2~9 去 0/1），约 1M 空间，重启服务器清空。

### V0.4 战斗确定性约定

- 共享 seed：服务器 START 下发 int seed；模拟器 `restart()` 前把 `simulator.shared_seed=seed`，`simulator.rng` 用 `RandomNumberGenerator` + `seed(seed)` 初始化；BotBrain 非联机模式下用 `seed+1` 初始化；联机模式下真人对手不使用 BotBrain。
- 单位迭代顺序：`player_units` 与 `bot_units` 必须以稳定顺序遍历（`unit_id` 升序 tie-break）；任何 for-each 顺序不得依赖字典哈希值。
- 随机数：所有模拟内随机（例如法术落点抖动、AOE 顺序、卡牌生成概率）必须使用 simulator.rng，禁止使用未初始化过的 `randi()` / `randf()`。
- CHECKSUM 算法：FNV-1a 32bit（offset=2166136261，prime=16777619），按顺序混合 `tick_count`、双方法力、基地血量、单位列表（按 side→unit_id 顺序，每个单位混合 `unit_id, art_id, level, hp, max_hp, speed_fp, damage, radius_fp, pos_fp.x, pos_fp.y, evolve_ts, attack_timer_fp, attack_cooldown_fp, target_id_hash`）、法术特效列表、进化闪光列表。
- 命令的"side"在联机中使用真实模拟器阵营：host→PLAYER，guest→BOT；host 与 guest 的出牌命令都携带自己的 side。命令字段全为 JSON 可序列化的 int/String/Bool/Array/Dictionary，禁止 GDScript 对象（例如 Vector2）出现在命令字典里。

### V0.4 联机协议（Godot ↔ Python 中继服务器）

**传输**：TCP 长连接；每个包为一行 UTF-8 JSON，分隔符 `\n`（0x0A）。无包头、无长度前缀、无需 TLS（V0.4 约定裸 IP+PORT，公网 HTTPS/WSS 待 V0.5）。

**客户端 → 服务器 请求包**：
```jsonc
// 创建房间
{"type":"CREATE_ROOM"}
// 加入房间（room_code 大小写不敏感，服务器统一大写）
{"type":"JOIN_ROOM","room_code":"ABC2"}
// 准备 / 取消准备；deck 为字符串数组（卡牌 id）
{"type":"READY","ready":true,"deck":["shield","swordsman",...]}
// 命令中继：payload 直接是 Lockstep 层的 Dictionary（PLAY_CARD_FP / NO_OP / CHECKSUM）
{"type":"COMMAND","payload":{"type":"PLAY_CARD_FP","tick":123,"side":"player","card_id":"shield","tgt_x_fp":35000,"tgt_y_fp":42000}}
// 结束汇报：winner 为 "host" / "guest" / "draw"
{"type":"RESULT","winner":"host","room_code":"ABC2"}
```

**服务器 → 客户端 推送包**：
```jsonc
// 创建响应
{"type":"ROOM_CREATED","room_code":"ABC2","my_side":"host"}
// 加入响应
{"type":"ROOM_JOINED","room_code":"ABC2","my_side":"guest"}
// host 端提示：guest 已加入
{"type":"PEER_JOINED"}
// 任一方 READY 状态变化时广播给对端（side=host/guest，ready=true/false）
{"type":"PEER_READY","side":"guest","ready":true}
// 双方都 READY → 服务器 START：seed 为共享随机种子，my_deck/peer_deck 是双方牌组，my_side 是本端角色
{"type":"START","seed":1738291041,"my_side":"host","my_deck":["s1",...,"s6"],"peer_deck":["g1",...,"g6"]}
// 命令转发
{"type":"COMMAND","payload":{...command dict...}}
// 结果广播（任一方发 RESULT 后服务器转发给双方）
{"type":"RESULT","winner":"host","room_code":"ABC2"}
// 对端断线（宽限 30s，客户端应暂停并显示倒计时；30s 后断线者负）
{"type":"PEER_DISCONNECT","grace_seconds":30.0}
// 30s 后断线方仍未回来，服务器判定胜者（通知在线的一方）
{"type":"OPPONENT_DISCONNECTED_WIN","winner":"host","room_code":"ABC2"}
// 错误
{"type":"ERROR","message":"room not found"}
```

### V0.4 联机控制器流程备忘（避免回归）

MAIN_MENU（展示已保存的 6 张当前牌组）
  ├─ 点"单机"：`online_mode=false` → `_start_battle()`（Bot 对手，strict_wait=false）
  ├─ 点"联机"：进入 ROOM_SETUP；可 `net.connect → CREATE_ROOM → ROOM_WAIT（host）`，或输入 4 位房间码后 `JOIN_ROOM → ROOM_WAIT（guest）`
  ├─ 点"图鉴"：进入 COMPENDIUM，上方详情、下方单位仓库
  └─ 点"牌组"：进入 DECK_BUILDER，上方编辑区、下方单位仓库；保存后覆盖当前牌组

ROOM_WAIT 双方准备：
  └─ 服务器 START：`online_mode=true, strict_wait=true, sides=[my_game_side,peer_game_side], simulator.shared_seed=seed → _start_online_battle`

BATTLE：
  ├─ 玩家出牌 → `scheduler.enqueue_command(cmd) + net.send_command(cmd)`
  ├─ CHECKSUM tick → `scheduler.enqueue_command(my_checksum) + net.send_command(...)`；对端 CHECKSUM 由 `_on_peer_command` 注入
  ├─ 断线 → 若收到 PEER_DISCONNECT：暂停 + 倒计时；若收到 OPPONENT_DISCONNECTED_WIN：直接结果页
  └─ 胜负：simulator 检测 winner → 客户端 REPORT → 服务器 RESULT 广播 → 双方结果页

RESULT：
  ├─ "重开"：走本地 `_start_battle()`（兼容旧按钮）
  └─ "主界面"：`_leave_room()`（断开 TCP、清状态、切回 MAIN_MENU）

## 临时实现原则

- 原型应小、清晰、可检查、易替换。
- 若实现游戏工程内容，应优先围绕 Godot 组织。
- 不要直接改动不理解的 `project.godot` 配置项；优先保持 Godot 编辑器生成的结构。
- 若只是辅助说明、数据验证或轻量外部工具，仍可在人类同意或任务需要时使用更轻量的脚本/网页原型。
- 卡牌、敌人、Buff、经济、遭遇、成长等规则优先使用结构化数据表达。
- 游戏设计数据应与渲染/UI 代码分离。
- 不引入大型依赖、游戏引擎、构建系统或外部服务，除非人类确认或现有工程已经采用。

## 代码风格占位约定

- 函数应围绕游戏领域意图命名。
- 核心对象应有清晰类型，例如卡牌、令牌、Buff、敌人、关卡、奖励、玩家状态。
- 战斗逻辑、经济规则、存档、随机生成不要依赖隐式全局状态。
- 随机行为应尽量可测试，例如使用种子 RNG 或可注入随机源。
- 平衡数值优先放在数据或配置中，除非它们属于基础公式。
- 对确定性规则、存档兼容、经济计算、战斗边界情况添加测试。
