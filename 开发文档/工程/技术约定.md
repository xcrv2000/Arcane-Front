# 技术约定

本文件记录工程任务需要读取的技术约束。当前项目已确认主要游戏工程使用 Godot；未确认的工程细节仍不得由 AI 擅自写死。

## 当前技术状态

- 已确认主要载体为 Godot 4.5 stable。
- Godot 工程位置：`游戏工程/`。
- Godot 项目文件：`游戏工程/project.godot`。
- `project.godot` 当前特征包含 `4.5` 与 `Mobile`。
- 当前渲染方式：`mobile`。
- 已确认 Godot 脚本语言使用 GDScript。
- 未确认辅助前端框架或外部工具栈。
- 未确认包管理器。
- 未确认构建命令。
- 未确认测试命令。
- `游戏工程/` 当前是 Godot 空项目，尚无玩法实现文件。
- 已确认主要目标用户为手机竖屏用户；工程和 UI 实现应优先考虑竖屏移动端体验。

## 技术栈确认规则

在没有人类设计师确认、也没有既有工程文件证明的情况下，AI 不得擅自写死尚未确认的技术细节。当前确认 Godot 4.5 stable 与 mobile 渲染方向，不代表目录结构、插件、导出目标、构建流程或测试流程已经确认。

当更多技术栈细节确认后，应补充：

- GDScript 版本与语言使用细则。
- 插件或第三方依赖。
- 目录结构约定。
- 安装命令。
- 本地启动命令。
- 构建命令。
- 测试命令。
- 移动端导出目标与导出配置。

## 坐标、速度与原型表现约定

- 对局地图的长边应作为 100 个逻辑单位处理，避免不同设备尺寸导致单位表现不同。
- 速度数值的单位是逻辑单位/秒；速度 1 表示每秒移动 1 个逻辑单位，速度 8 表示每秒移动 8 个逻辑单位。
- 实现时应优先让战斗逻辑使用逻辑单位，再按当前视口尺寸换算到屏幕像素。
- 不应把设备像素值作为权威移动速度或战斗距离。
- V0.1 中单位不需要美术资源；每个生物可用 Godot 绘制的简单几何图形（圆、三角、方）加一个字表示。

## 临时实现原则

- 原型应小、清晰、可检查、易替换。
- 若实现游戏工程内容，应优先围绕 Godot 组织。
- 不要直接改动不理解的 `project.godot` 配置项；优先保持 Godot 编辑器生成的结构。
- 若只是辅助说明、数据验证或轻量外部工具，仍可在人类同意或任务需要时使用更轻量的脚本/网页原型。
- 卡牌、敌人、Buff、经济、遭遇、成长等规则优先使用结构化数据表达。
- 游戏设计数据应与渲染/UI 代码分离。
- 不引入大型依赖、游戏引擎、构建系统或外部服务，除非人类确认或现有工程已经采用。

## 代码风格占位约定

- 函数应围绕游戏领域意图命名。
- 核心对象应有清晰类型，例如卡牌、令牌、Buff、敌人、关卡、奖励、玩家状态。
- 战斗逻辑、经济规则、存档、随机生成不要依赖隐式全局状态。
- 随机行为应尽量可测试，例如使用种子 RNG 或可注入随机源。
- 平衡数值优先放在数据或配置中，除非它们属于基础公式。
- 对确定性规则、存档兼容、经济计算、战斗边界情况添加测试。
